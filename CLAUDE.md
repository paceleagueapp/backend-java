# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## ⛔ NEVER deploy without an explicit command

**`git push` to `main` = an immediate production deploy** (GitHub Actions → ECR → SSM → live on `api.paceleague.co.kr` + `paceleague.co.kr`). Because of that:

- **NEVER run `git push`** until the user says "커밋 푸시" / "푸시해" / "배포해" (or clear equivalent) **in that same message.** Not implied by "구현해 / 재구현 / 고쳐 / 만들어줘 / 직접 적용해" — those mean *write code + tests + local commit, then stop.*
- **NEVER deploy by any other route either** — no SSM redeploy, no manual image swap, no triggering the workflow — unless explicitly told.
- Found a bug mid-task? Fix it locally, commit locally, report it. The user decides when it ships.
- Applying a DB migration when asked ("직접 적용해") is fine *for the DB*, but still does not authorize a code push.
- Once the user *does* say push: push, then stop — don't poll CI or curl prod unless asked.

(This has been violated repeatedly; the user has asked more than once. Treat it as a hard rule.)

## Project

PaceLeague — a Spring Boot backend for a running-record and ranking service. Users log runs, the server computes pace/calories/score, and members are ranked by season/tier.

This is a **monorepo** with two independently-managed parts deployed together:

- **`api/`** — the Spring Boot backend (everything described below). Serves `api.paceleague.co.kr`.
- **`web/`** — `index.html` is the landing page **and** the community feed in one, reddit.com-style: the board feed (tabs/sort/post list) is visible to everyone, logged in or not; the header shows a login button when logged out or nickname/write/logout when logged in. Posting, commenting, and voting require login (redirect to `login.html` if attempted while logged out) — only reading is public. `post.html` (detail/comments/voting) and `login.html` are separate pages; all pages share `js/app.js` for auth/fetch helpers and `css/app.css` for the shared design system (topbar + inline nav / mobile bottom tab bar, buttons, cards, tier badges, form controls — page-specific CSS stays inline in each page's `<style>`, which loads after and can override), and call the `board`/`member` APIs directly from the browser. **2026-09-08: the whole site was restyled to a light "race-dashboard" look (`C-1`) — slim dark topbar with the 커뮤니티/랜드잇/크루 menu inline between logo and login, off-white `#eef0f3` canvas, white shadow cards, tier-colored badges, medal-colored 1·2·3 ranks; on mobile the inline nav collapses to a fixed bottom tab bar. Nav labels are set from `data-navkey` attrs (both `.navlink` and `.bnav`) via `t(...)`.** Plus the ko/en privacy/terms/account-deletion pages required for app store compliance. Serves `paceleague.co.kr` / `www.paceleague.co.kr`. No build step, no framework — plain multi-page HTML/vanilla JS served directly by Nginx (deliberately kept this way even for the community feature — see `docs/architecture.md`).

A single push to `main` deploys both (see Deploy below) — there is no separate pipeline for `web/`.

## Commands

Run all Gradle commands from `api/` (or pass `-p api`):

```bash
cd api && ./gradlew bootRun          # run locally (Windows: gradlew.bat bootRun)
cd api && ./gradlew test             # run all tests (JUnit 5)
cd api && ./gradlew test --tests "com.paceleague.SomeTest"   # run a single test class
cd api && ./gradlew clean build      # full build (used by CI/Docker, run with -x test to skip tests)
```

Local run requires a `local` Spring profile with env vars: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET` (see `api/src/main/resources/application-local.yml`), plus a running MySQL and Redis (Redis defaults to `127.0.0.1:6379`). `.env` lives at `api/.env` (gitignored) since that's the working directory `./gradlew bootRun` runs from.

## Deploy (single pipeline for api/ + web/)

`docker build -t paceleague .` is run from the **repo root** (build context spans both `api/` and `web/`) — the Dockerfile builds the `api/` jar in a builder stage, then in the final image also `COPY web /web-dist` so the static site travels inside the same image as a distribution artifact (the Spring Boot app does not serve it).

GitHub Actions deploys on push to `main` (`.github/workflows/deploy.yml`) — **so an agent must not `git push` without an explicit command from the user; see the ⛔ rule at the top of this file.** It builds the jar from `api/`, builds/pushes the Docker image to AWS ECR, then triggers `.github/ssm-commands.json` on EC2 via SSM, which — in this order, deliberately, so a web-asset-extraction failure can never delay or block the app coming back up:
1. pulls the new image and **restarts the `paceleague` app container first** (serves `api.paceleague.co.kr` via Nginx reverse proxy on port 8080) — this is the priority; the app must not stay down
2. only then extracts `/web-dist` from the same image into a temp dir and swaps it into `/var/www/paceleague` (what Nginx serves for `paceleague.co.kr`), guarded so a failed extraction leaves the previous static site in place rather than deleting it

So `api.paceleague.co.kr` and `paceleague.co.kr` both update together from one push — see `docs/infra.md` for the full Nginx/domain wiring on the EC2 host.

Local Docker smoke test: `docker build -t paceleague .` / `docker run -d -p 8080:8080 --name paceleague paceleague` (run from repo root, not `api/`).

## Architecture

**2026-08-10: converted to Clean Architecture (use-case + ports & adapters) at the user's explicit request** — see `docs/architecture.md` for the full rationale, since this is a deliberate, documented exception to `AGENTS.md`'s normal "no unrequested abstraction / no large-scale refactor" rules. Still a single Gradle module (no multi-module split).

Each domain package under `com.paceleague` follows: `domain/{entity,policy,enums}` (JPA entities used directly as domain models, not split into a separate framework-free model — see architecture.md for why), `application/port/{in,out}` + `application/{service,dto}` (use-case interfaces/impls, output ports have zero Spring Data/JPA imports), `adapter/{in/web, out/persistence}` (controllers depending only on `port/in`; `*JpaRepository` + `*PersistenceAdapter` implementing `port/out`). Naming (2026-09-04 normalization): inbound use-case interfaces are `*UseCase` (`member`/`record`/`board`/`media` previously kept pre-refactor `*Service` names), and every use-case impl in `application/service/` is `*Service` with **no `Impl` suffix** (`RecordService implements RecordUseCase`, `SaveGpsSessionService`, `RankQueryService` for multi-interface ones — `application/service/` has zero `*Impl` classes). Interfaces built specifically for another domain to call in live in `application/port/in/shared/` (`GetMemberNicknamePort`, `rank.shared.ApplyScoreUseCase`, `season.shared.GetCurrentSeasonPort`, etc.); a domain's own use-case that another domain merely reuses (`record.RecordQueryUseCase`, `media.MediaUseCase`) stays in plain `port/in/`. Only two things get ported: a domain's own JPA repository, and genuine cross-domain repository reach (e.g. `record` now depends on `season.shared.GetCurrentSeasonPort` + `rank.shared.ApplyScoreUseCase` instead of importing `rank`/`season` repositories directly). Generic infra clients (`StringRedisTemplate`, `TranslateClient`, `PasswordEncoder`) are injected directly into use-case impls, not portified. `common/` stays as shared-kernel config/error/response/security (plus a new `common/web` for the `@MemberSno` argument resolver — see Auth flow below); `JwtTokenProvider` lives in `common/security/jwt/`, not under `member`, since `JwtAuthenticationFilter`/`SecurityConfig` depend on it directly. See `AGENTS.md` for the full rule set this codebase is meant to follow (Java/Gradle only, no Kotlin/Maven, minimal abstraction beyond what's described above, no multi-module split — the `api/`+`web/` monorepo split is a deployment-unit split, not the kind of multi-module Gradle setup that rule is about).

Domains: `member` (auth), `record` (running logs), `rank` (individual score/tier), `ranking` (leaderboard), `season` (no controller — only exposes `GetCurrentSeasonPort` for other domains), `appversion` (mobile force/soft update check), `board` (community: boards/posts/comments/votes), `territory` (러닝 땅따먹기 / land-grab game — closed GPS loops become hex-grid "땅"; a later run captures whichever hexagons it overlaps from an existing owner, no HP; `GET /api/territory/map` for the map), `crew` (크루/guild — one member = one crew, invite by member search / apply & approve, leader manages; `/api/crew/**`), `notification` (FCM 푸시 — no controller; `DailyTerritoryDigestScheduler` sends a daily "yesterday N users captured M 땅" topic broadcast at 09:00 KST, gated `paceleague.fcm.daily-digest.enabled`, off by default), `admin` (관리자 웹패널 auth — completely separate account system from `member`, Redis-backed server session instead of JWT; `/api/admin/**`), `common` (cross-cutting config/response/error/web).

Note the `rank` vs `ranking` split — they are separate packages by design, not duplicates: `rank` answers "what's my score/tier" (`GET /api/rank/me`), `ranking` answers "show me the leaderboard" (`GET /api/ranking/getRanking`).

### Auth flow

JWT-based, stateless (`SecurityConfig`, `sessionCreationPolicy(STATELESS)`).

- Public endpoints: `/api/member/join`, `/login`, `/reissue`, `/logout`, `/api/app/version-check`, `/api/ranking/top10`, `/api/common/language`, Swagger paths (permitAll in `SecurityConfig`, but the `prod` profile disables springdoc entirely via `springdoc.api-docs.enabled=false`/`swagger-ui.enabled=false` — Swagger UI + `/v3/api-docs` are 404 in production, local-only), plus four `GET`-only `/api/board/**` reads (list boards, list posts, post detail, list comments — method-scoped via `HttpMethod.GET` matchers in `SecurityConfig`, since the same paths' `POST`/`DELETE` still require auth), plus `GET /api/territory/map` and `GET /api/territory/ranking` (land-grab map + area ranking, method-scoped, public — logged-in only fills the `mine` flag), plus `GET /api/crew/search` (crew search, method-scoped, public — all other `/api/crew/**` incl. `GET /api/crew/{sno}` and `/api/crew/me` require auth), plus `/api/admin/login` (admin panel login — everything else under `/api/admin/**` needs a valid `X-Admin-Session`, a completely separate Redis-session scheme from member's JWT, see the admin domain section below). Everything else requires a valid access token.
- CORS is otherwise closed. Nine registrations exist in `common.config.CorsConfig`, all scoped to `paceleague.co.kr`/`www.paceleague.co.kr`: `/api/ranking/top10` (GET only, the original public-landing-page exception), `/api/member/**` and `/api/board/**` (GET/POST/PUT/DELETE + `Authorization`/`Content-Type` headers, added so `web/index.html`/`login.html`/`post.html` can call auth and community endpoints from the browser), `/api/record/recent-30-days`, `/api/territory/map`, `/api/territory/ranking` (all three share the `getWithAuthHeader` config — GET only + `Authorization` header allowed: `recent-30-days` needs auth for the board post-creation "attach my run" dialog; the two `territory` reads are public but `web/js/app.js`'s `apiFetch` still attaches `Authorization` for a logged-in user — 2026-09-07: without allowing that header the logged-in preflight got a 403/CORS error and the map+ranking never loaded, so `readOnlyPublic` was wrong for these two), `/api/media/**` (GET/POST + `Authorization`/`Content-Type`, same shape as `/api/board/**`, for the presigned-upload media flow — see "Board post ↔ media attachment" below; note this is separate from the `paceleague-media` S3 bucket's own CORS config, which is what actually lets the browser `PUT` a file straight to S3), `/api/crew/**` (`authAndBoard` shape — GET/POST/PUT/DELETE + `Authorization`/`Content-Type`, for `web/crew.html`; `/api/member/search` is already covered by the `/api/member/**` entry), and `/api/admin/**` (GET/POST/PUT/DELETE + `X-Admin-Session`/`Content-Type` — a distinct header from `Authorization` since admin sessions are a separate Redis-backed scheme, not JWT; see the admin domain section below). A `local`-profile-only bean additionally allows `http://localhost:*` for dev. Don't widen this further without a reason — every other `record` endpoint, plus all of `rank`/`appversion`, has no CORS headers and can't be called from a browser on a different origin.
- `JwtAuthenticationFilter` runs before `UsernamePasswordAuthenticationFilter`, validates the access token, and puts a `JwtAuthenticationFilter.AuthPrincipal(memberSno)` on the `Authentication`. Controllers pull the current user via a `@MemberSno Long memberSno` parameter (`common.web.MemberSnoArgumentResolver`, added in the 2026-08-10 Clean Architecture pass) — before that, every authenticated controller repeated its own `((AuthPrincipal) authentication.getPrincipal()).memberSno()` cast. `@MemberSno(required = false)` is used by `BoardController`'s public read endpoints to get `null` instead of an exception when unauthenticated.
- Access tokens are short-lived JWTs (`JwtTokenProvider`); refresh tokens are opaque random strings stored in Redis with TTL (`RefreshTokenService`, key prefix `refresh:`), not JWTs. `/reissue` rotates the refresh token (old one revoked, new one issued).
- Password hashing via `BCryptPasswordEncoder` (Spring Security is used only for auth mechanics here, not full MVC integration).

### Response/error conventions

- All controller responses wrap in `ResponseApi<T>` (`success`/`code`/`message`/`data`/`timestamp`) via `ResponseApi.success(...)`.
- `GlobalExceptionHandler` (`@RestControllerAdvice`) maps `IllegalArgumentException` → 400, `MethodArgumentTypeMismatchException`/`MissingServletRequestParameterException` (bad/missing query or path param, e.g. `zoom=16.5` into an `int`) → 400 (added 2026-09-07), `NoResourceFoundException` (unknown path) → 404, and everything else → 500, all as `ApiError` bodies with `ErrorCode`. Domain/service-layer validation failures should throw `IllegalArgumentException` to get a proper 400 rather than falling through to the generic 500 handler. (The 404 handler was added 2026-08-27 because disabling springdoc in prod routed `/swagger-ui.html`·`/v3/api-docs` into the catch-all as 500s.)

### Record calculations

`RecordSummaryCalculator` (in `record.domain.policy`) is the pace/calorie math: distance in meters → km, pace = duration / distance rounded HALF_UP, calories = weight(kg) × distance(km) (a rough linear approximation, not a real MET-based formula). `RecordScoreCalculator` (same package) holds the pure base-score/pace-bonus math extracted out of `RecordService` during the Clean Architecture pass. `RankTierPolicy` (in `rank.domain.policy`) derives a `RankTier` from a raw score by finding the highest tier whose `minScore` the score clears.

Known gap: `RecordController.getMonthAll` hardcodes `weightKg = 70` instead of reading the member's actual weight (marked with a TODO in the code).

### GPS chunk ingest (`POST /api/record/gps`)

2026-08-27: the mobile app posts a **GPS coordinate chunk every 5 minutes during a run** (not one payload at the end); the member is identified by access token only (`@MemberSno`). `SaveGpsSessionUseCase.ingest` / `SaveGpsSessionService` accumulate chunks of the same run — keyed by `clientRunId` — into **one `record_track` row** (`status=ACTIVE`, `record_sno` null). The coordinate array is appended into `record_track.points_json` (LONGTEXT, parse→addAll→re-serialize each chunk — fine at this scale: a 2h run ≈ 2500 points ≈ ~9MB total write over the run); distance is computed server-side from the coordinates via `GeoDistanceCalculator` (haversine, `record.domain.policy`, pure + unit-tested), bridging chunks through `last_lat`/`last_lng`. Duplicate/resent chunks are deduped by the `last_point_at` watermark (only points strictly after it are stored → `skippedPoints` in the response). When a chunk carries `finished: true`, the service **reuses `RecordUseCase.create`** once (same distance/pace validation, same 1-month duplicate-`startTime` rule, same `Rank`/`MemberScore` effects as `/api/record/save`) with the accumulated distance + start/end, sets `record_track.status=FINISHED` + `record_sno`. A `finished` chunk that fails `RecordUseCase.create` validation rolls back and leaves the session `ACTIVE` for the app to retry. `GpsSessionValidator` (pure + unit-tested) does per-chunk shape checks (`activityType` optional/RUNNING, coord ranges, `recordedAt` required, ≤2000 points/chunk, ≤60000/run, empty `points` allowed only when `finished`). Timestamps arrive ISO-8601 UTC → `GpsSessionRequest` uses `OffsetDateTime`, service converts to UTC `LocalDateTime`. Mobile-only — no CORS entry. Migrations: `docs/migrations/2026-08-27_record_gps_track.sql` then `..._record_track_streaming.sql`.

Abandoned sessions (`ACTIVE` runs whose app died before sending `finished`) are swept by `GpsSessionSweeper` (`record.adapter.in.scheduler`, `@Scheduled` every 5 min after a 2 min initial delay — one of two scheduled jobs, the other being `notification.DailyTerritoryDigestScheduler`; `common.config.SchedulingConfig` carries the `@EnableScheduling`). It finds `ACTIVE` `record_track` rows idle (`update_at`) longer than `paceleague.gps.sweeper.idle-minutes` (default 30), and per session — each in its own transaction, driven from the scheduler so Spring's proxy applies — calls `SaveGpsSessionUseCase.finalizeSession` (same finalize path as a `finished` chunk); if that throws (no points, implausible pace/distance) it calls `abandonSession` → `status=ABANDONED` so the next sweep skips it. Gated by `paceleague.gps.sweeper.enabled` (default true); **single-instance only — needs ShedLock or similar before the app scales past one instance.** Deliberately not a message queue: at ~33 req/s worst case the chunk path is a `SELECT`+`UPDATE`, and the project keeps infra minimal (see the Rekognition "no SNS/webhook" note).

### 러닝 땅따먹기 / Territory land-grab (`territory` domain)

2026-08-27, first slice of the Notion "러닝 땅따먹기" spec. **Opt-in per run**: the app sends `territoryMode: true` on the first `POST /api/record/gps` chunk → `record_track.territory_mode = 1` (fixed at session creation). Only those sessions trigger land-grab logic at run finish (`finished:true` chunk **or** `GpsSessionSweeper` auto-finalize). Backward-compatible — no field / `false` = a normal run, so this is inert until the mobile app opts in.

`SaveGpsSessionService.finalizeRun` → `territory.ProcessTerritoryRunUseCase.process` (cross-domain, same direction as `record→rank`'s `ApplyScoreUseCase`; `territory` never depends on `record` — coords are passed by value in the command). It's **best-effort**: `ProcessTerritoryRunService` is `@Transactional(REQUIRES_NEW)` and `finalizeRun` catches+logs, so a failed/rejected land claim never rolls back the run/score.

Rules (`ProcessTerritoryRunService`, all thresholds in `TerritoryProperties` = `@ConfigurationProperties("paceleague.territory")`, registered in `PaceleagueApplication`'s `@EnableConfigurationProperties`, defaults in the record's compact constructor, nothing in yml):
- **Closed loop?** `ClosedLoopDetector` — start/end within `close-threshold-meters` (50). Else no-op.
- **Valid shape?** `PolygonGeometry` (JTS) + `TerritoryClaimValidator` — perimeter ≥ `min-perimeter-meters` (300), area in `min-area-sqm` (10k) … `max-area-sqm` (5M). Else no-op.
- **Overlaps existing `ACTIVE` territory, hexagon by hexagon** (2026-09-07: per-hex, not whole-territory — see dated entry below): for each covered hexagon already owned by someone — mine → left alone; someone else's → that single hexagon is taken, unconditionally, HP-free (the HP/attack/heal/`territory_contribution` system was removed 2026-09-05 — see below). The run this hexagon belongs to *now* always wins, regardless of how long the previous owner had held it.
- **Free hexagons + hexagons just taken from others** → merged into one new `Territory` for this run (`season` = current season number snapshot). Hexagons that were already mine are left out (they stay part of whatever territory already owns them). A territory that loses some but not all of its hexagons shrinks in place; one that loses every hexagon is deleted.

**JTS** (`org.locationtech.jts:jts-core`, new dep — pure Java, no transitive deps) does polygon area/intersection. No spatial DB types — `polygon_json` LONGTEXT + `DECIMAL` bbox columns, geometry computed in Java via an equidistant planar projection (same "coords as JSON, math in Java" approach as `record_track.points_json`). `ClosedLoopDetector` reuses `record.domain.policy.GeoDistanceCalculator` directly (pure-static cross-domain call, same documented exception as `BoardQueryService` → `RankTierLabelPolicy`).

`GET /api/territory/map?swLat=&swLng=&neLat=&neLng=&zoom=&lang=` (public, `@MemberSno(required=false)`): `ACTIVE` territories whose bbox overlaps the map bounds, capped at `map-max-results` (300), largest first; `zoom < min-zoom` (13) → empty list + `zoomTooLow:true`. Owner nickname via `member.GetMemberNicknamePort`, tier via `rank.GetMemberTierPort` (per-owner cached). `web/territory.html` (Google Maps JS API, plain page, needs a `GOOGLE_MAPS_API_KEY` — placeholder in the file, user must supply a referrer-restricted key) renders polygons + owner InfoWindows. Migration: `docs/migrations/2026-08-27_territory_feature.sql`. **Single-instance only** (pessimistic locks, like the sweeper).

**2026-09-05: ownership/overlap switched from raw-polygon intersection to an H3 hex grid (resolution 12), HP kept at the territory level** (per explicit user request — claim the full set of hexagons a run's closed loop contains or touches, not just the exact run shape). New dep `com.uber:h3:4.5.0` (JNI + bundled native libs, unlike pure-Java JTS). `ClosedLoopDetector`/`TerritoryClaimValidator`/`PolygonGeometry` still validate the actual run polygon unchanged; only a validated polygon then gets converted via `H3TerritoryGrid.coverRing` using `H3Core.polygonToCellsExperimental(..., PolygonToCellsFlags.containment_overlapping)` (cells fully inside *or* touching the loop). New table `territory_hex` (`h3_index` PK, `territory_sno`, `season`) maps each hexagon to a territory — the PK doubles as a DB-enforced invariant that a hexagon belongs to at most one ACTIVE territory. Capture never touches this mapping, only flips `territory.owner_member_sno` (same as before), so `TerritoryDamagePolicy` is unchanged — it now just receives overlapping/total hex counts instead of overlap/total sqm, same ratio formula. Concurrency: `ProcessTerritoryRunService` now aggregates hit territories via a `territory_hex`⋈`territory` query, then `PESSIMISTIC_WRITE`-locks only those specific rows (`TerritoryRepositoryPort.findAllByIdForUpdate`, replacing the old bbox-wide `findActiveIntersectingBboxForUpdate`) — still single-instance only. `territory.polygon_json` for a newly-created territory is now the union outline of its owned hexagons (`H3TerritoryGrid.unionBoundaryLatLng`, JTS `UnaryUnionOp`), computed once at creation, so `GET /api/territory/map`'s response shape is unchanged. `area_sqm` is now the summed hex-cell area (so the area ranking reflects actual owned land); `perimeter_m` still stores the real run's perimeter (validation-only). New `hex_count` column on `territory` (fixed at creation) avoids a `COUNT(*)` per interaction. Migration: `docs/migrations/2026-09-05_territory_hex_grid.sql` — **schema only**; ACTIVE territories created before this change have no `territory_hex` rows and become permanently non-interactive "ghost land" (still rendered on the map, but can never be attacked/captured again) unless separately backfilled by re-running `H3TerritoryGrid.coverRing` over their old `polygon_json` — not done automatically since H3 encoding needs application code, not SQL.

**2026-09-05 (same day, follow-up): HP removed entirely — overlap now means unconditional, immediate capture.** Per explicit user request. Deleted `TerritoryDamagePolicy` (+ its test), `TerritoryContribution` entity/port/JPA-repo/adapter, and the `hp`/`max_hp` columns (`territory.capture` no longer resets anything, just flips owner) and `defaultMaxHp`/`attackFactor`/`healFactor`/`contributionWindowMinutes` from `TerritoryProperties`. `ProcessTerritoryRunService`'s overlap branch is now: mine → no-op (but still blocks new-territory creation, "빈 땅이면 즉시 내 땅" unchanged); someone else's → `target.capture(runner)` immediately, no ratio/threshold/contribution-window logic at all. `TerritoryView`/`GET /api/territory/map` no longer returns `hp`/`maxHp` (`web/territory.html`'s InfoWindow no longer shows an HP line) — this narrows that endpoint's response shape, but `ProcessTerritoryRunResult` (the GPS-finalize response surfaced to the mobile app via `GpsSessionResponse.territoryResult`) keeps its `damagedTerritorySnos`/`healedTerritorySnos` fields for now (always empty going forward) rather than changing that contract without app-side coordination — same caution as the `record` `weightKg` TODO. Migration: `docs/migrations/2026-09-05_territory_remove_hp.sql` (run after the hex-grid one above) — drops `territory.hp`/`max_hp` and the whole `territory_contribution` table.

**2026-09-07: overlap capture switched from whole-territory to per-hexagon** (explicit user request — "겹치면 겹친 부분만 뺏도록", i.e. only the overlapping hexagons should change hands, and whichever run touches a hexagon *later* always owns it, no matter who claimed it first). `ProcessTerritoryRunService.captureAndClaim` (replacing the old `captureOverlapping`) now works off `TerritoryHexRepositoryPort.findActiveOwners` — per-hexagon ownership (`h3_index` → `territory_sno`), not the old `findActiveOverlapCounts` territory-level aggregate — and splits this run's covered hexagons three ways: already mine (left alone), free (claimed), someone else's (taken). Free + taken hexagons are merged into **one new `Territory` row for this run** via the same `createTerritoryFor` helper the old no-overlap path used (so a single run can now both capture land *and* create new land in the same call). Each victim territory is re-derived from its *remaining* hexagons only (`Territory.recomputeFromHexes`, renamed from the H3-backfill-only `applyHexBackfill` since it now has two callers) — `polygon_json`/`area_sqm`/`hex_count`/bbox shrink to match; if nothing remains, the row is deleted (`TerritoryRepositoryPort.delete`, new). `Territory.capture()` (whole-row owner flip) is gone — a territory's `owner_member_sno` genuinely never changes anymore; ownership only moves by hexagons migrating to a freshly-created row (`h3_index` PK doubles as an upsert key, so `saveAll` both inserts newly-free hexagons and re-points captured ones to the new `territory_sno` in one call). `ProcessTerritoryRunResult.interacted(...)` gained a `createdTerritorySno` parameter — `Outcome.INTERACTED` can now carry a non-null `createdTerritorySno` alongside `capturedTerritories` (previously the two were mutually exclusive with `Outcome.CREATED`); `damagedTerritorySnos`/`healedTerritorySnos` are unchanged (still always empty, kept for app-contract stability per the 2026-09-05 HP-removal note above). No migration — same tables, only the query/capture logic and one JPA repository method (`findActiveOwners` replacing `findActiveOverlapCounts`) changed. **Not retroactively applied to existing production territories**: the old whole-territory captures already recorded in `territory`/`territory_hex` are left as-is (correctly reprocessing them would mean replaying every historical territory-mode run through the new algorithm from a data source — record_track history — that was never linked back to *capturing* runs specifically; see chat for the discussion of why this needs its own explicit go-ahead rather than being folded into the code fix).

### Board post ↔ media attachment (images/videos/links) + Rekognition moderation

2026-08-11: added a `media` domain (`api/.../media/`) so posts can attach images, videos, and links, mirroring `record`/`rank`'s query-vs-write use-case split (`MediaUseCase` for writes, `MediaQueryService implements GetPostAttachmentsPort` for reads). Upload flow is presigned-URL-direct-to-S3 (backend never proxies file bytes): `POST /api/media/uploads` issues a 5-minute presigned PUT URL against bucket `paceleague-media` and creates a `PENDING` `Media` row; the browser PUTs the file straight to S3; `POST /api/media/{id}/complete` triggers moderation — images synchronously via Rekognition `DetectModerationLabels` (result known immediately), videos asynchronously via `StartContentModeration` (stays `PENDING`, client polls `GET /api/media/{id}/status` which re-checks `GetContentModeration` on each call — no SNS/webhook, deliberately kept infra-free). Confidence ≥60 on any label → `REJECTED`, and the S3 object is deleted immediately on rejection (size-exceeded or moderation-flagged) since the bucket's `media/` prefix is public-read and a rejected object must not keep existing there even unlinked. Links skip upload/moderation entirely (`POST /api/media/links`, `APPROVED` immediately) but are restricted to `http(s)://` schemes since the URL lands in an `<a href>` client-side (XSS guard).

`PostCreateRequest.attachmentMediaIds` (max 10) only gets linked to the post *after* `postRepositoryPort.save(post)` inside `BoardService.createPost` — unlike record attachment, media can't be validated before the post exists because `Media.postSno` isn't set until then, so `MediaUseCase.attachToPost(...)` runs post-save and any validation failure (not owned, not `APPROVED`, already attached elsewhere) rolls back the whole transaction, post insert included. `PostSummaryResponse.attachmentCount` / `PostDetailResponse.attachments` are resolved the same way `attachedRecord` is — via `GetPostAttachmentsPort`, no owner check, since any viewer can see a public post.

**Infra status as of 2026-08-11: fully provisioned.** The agent created and configured the `paceleague-media` S3 bucket directly via AWS CLI this session (bucket, public-access-block, bucket policy scoping public reads to `media/*`, bucket CORS for browser PUT) — see `docs/infra.md`. It initially could **not** attach the needed IAM inline policy (`s3:PutObject`/`GetObject`/`DeleteObject` + the three Rekognition moderation actions) to the EC2 instance role `paceleague-s3-read`, because `github-actions-deploy` lacks `iam:PutRolePolicy`; the user attached it via the AWS console instead, and the agent verified it took effect by running `s3:PutObject`/`HeadObject`/`DeleteObject` and `rekognition:DetectModerationLabels` directly on the EC2 instance via SSM (using the instance's own role credentials) — see `docs/infra.md`'s media section for the exact policy JSON and verification commands if this ever needs redoing (e.g. after an instance/role replacement).

### Board post content is now sanitized HTML, not plain text (inline rich-text editor)

2026-08-11 (same day, follow-up): the plain `<textarea>` + detached upload-chip UI from the previous entry was replaced with an actual inline WYSIWYG editor (`contenteditable` in `web/index.html`, toolbar limited to Bold/Italic/Link/Image/Video — no headings/lists, by explicit user choice) where images/videos/links get inserted directly into the content at the cursor instead of listed separately below it. This makes `Post.content` **attacker-influenced HTML** rather than plain text for the first time — the board is publicly readable and `web/js/app.js` keeps JWTs in localStorage, so unsanitized stored HTML would be a straight path to token theft via XSS.

`board.domain.policy.PostContentSanitizer` is the (only) place this gets sanitized, called from `BoardService.createPost` before the sanitized string is ever persisted — reads (`post.html`) trust it and render via `innerHTML` directly, no re-sanitizing on the way out. It wraps OWASP Java HTML Sanitizer (`com.googlecode.owasp-java-html-sanitizer:owasp-java-html-sanitizer:20260313.1`, version confirmed against Maven Central at implementation time, not guessed) with a **custom `HtmlPolicyBuilder`** rather than the library's bundled `Sanitizers.FORMATTING`/`LINKS`/`IMAGES` — those bundles allow a much wider tag set (`font,s,u,o,sup,sub,ins,del,strike,tt,code,big,small,span`, etc.) than the "Bold/Italic/Link only" scope calls for, and none of them know about `<video>` anyway. Final allowlist: `p, br, div, b, strong, i, em, a[href], img[src,alt], video[src,controls]` — everything else (script, style, `on*`, `class`, `javascript:` URLs) is dropped by the library's default-deny behavior. "Blank content" was redefined to account for this: `PostContentSanitizer.toPlainText(...)` (regex-based tag stripping — safe here specifically because it only ever runs on already-sanitized output, not attacker input directly) extracts plain text, and a post is valid if that's non-blank OR `containsMedia(...)` finds an `<img`/`<video>` tag, so image/video-only posts with no caption are allowed.

`TranslationService.translatePost` had to change too: AWS Translate doesn't understand HTML, so translating the raw sanitized content would garble the markup — it now translates `PostContentSanitizer.toPlainText(post.getContent())` instead, and skips calling Translate entirely (returns `""`) when that's blank (image-only post), both to avoid an AWS Translate empty-input error and to not pay for a no-op call. `post.html`'s translation toggle was updated to match: original content goes through `innerHTML` (it's HTML), translated content stays `textContent` (it's always plain text now, regardless of what the original looked like).

The existing `media` domain/pipeline from the entry above is **unchanged** — the editor just redirects the same presign→PUT→complete→poll flow's result (an approved `url`) into an inline `<img>`/`<video>` at a saved cursor placeholder (`<span data-media-pending="true">`, tracked by DOM id since the upload is async and stays valid even if the user clicks elsewhere meanwhile) instead of a chip list. `PostCreateRequest.attachmentMediaIds` and `POST /api/media/links` still exist in the API (harmless for other clients) but the web editor no longer sends/calls them — media URLs live directly in `content` HTML now, and links are inserted client-side via `document.execCommand('createLink', ...)` with no upload/moderation round-trip needed, relying on the sanitizer's URL-protocol allowlist as the only server-side check. `PostDetailResponse.attachments` is unchanged API-side, but `post.html` no longer renders the separate attachments gallery block (would duplicate what's already inline in `content`).

### Post edit, list thumbnails, and a shared editor module (fixing the "attachmentCount always 0" gap above)

2026-08-11 (third follow-up, same day): three fixes/additions on top of the rich-text editor work above, done together since the first two exposed real gaps in it:

### 관리자 웹패널 (`admin` domain) — 5개 메뉴 모두 구현 (설정은 앱 버전만)

2026-09-10 (committed locally, not yet deployed — no new migration needed for the content below, all five menus read/write existing tables). First cut was `/admin` login + layout + left-nav menu shell only, each menu page a placeholder ("상세내용은 내가 다시 말해줄게"); same day, all five menus got their actual content once the user specified it one at a time.

- **Completely separate account/session system from `member`** — no shared table, no shared auth code. `admin` table (`docs/migrations/2026-09-10_admin_feature.sql`, `admin_id`+`password_hash` only) has **no signup endpoint at all**; the first account must be inserted directly into the DB (BCrypt hash) by an operator, same manual-provisioning pattern as any other one-off admin task in this repo.
- **Redis server session, not JWT** — explicit user requirement ("로그인한 세션은 redis로 관리"), unlike member's stateless JWT+refresh-token pair. `POST /api/admin/login` (public) checks `admin_id`/password via `AdminAuthService` (`admin.application.service`) and issues an opaque random token (`RedisAdminSessionAdapter`, same "random string + Redis TTL" shape as member's `RedisRefreshTokenAdapter`, key `admin:session:<token>` → adminSno, 12h TTL). The client sends it back as `X-Admin-Session` (a custom header, not `Authorization`, to keep it unambiguously separate from member JWTs — the two schemes can coexist in the same browser without collision). `common.security.AdminSessionFilter` (same architectural slot as `JwtAuthenticationFilter` — a common/security primitive, not portified, since request-time validation is a pure Redis lookup) reads that header on every request, and **slides the TTL back to 12h on each valid request** so an active admin session never expires mid-work. `POST /api/admin/logout` revokes the Redis key immediately (the actual point of using a server session instead of JWT: instant server-side revocation). `GET /api/admin/me` is what the frontend polls on every protected page load to confirm the session is still valid.
- **`@AdminSno`** (`common.web`, mirrors `@MemberSno`/`MemberSnoArgumentResolver` exactly but resolves `AdminSessionFilter.AdminPrincipal` instead) is how `AdminController` gets the current admin's sno. `SecurityConfig` permits only `/api/admin/login`; everything else under `/api/admin/**` relies on `AdminSessionFilter` having set an `Authentication` — no header/invalid token means `anyRequest().authenticated()` 401s before the controller ever runs, same mechanism as every other authenticated endpoint. `CorsConfig` registers `/api/admin/**` with `GET/POST/PUT/DELETE` + `X-Admin-Session`/`Content-Type` headers (PUT/DELETE allowed pre-emptively since 회원관리 등 CRUD screens are obviously coming next).
- **Web**: `web/admin/index.html` is the login page (bare `/admin` resolves to this via Nginx's default directory-index behavior — no repo-side routing needed since `web/` is plain static files). `web/admin/{members,ranking,records,territory,settings}.html` are the five menu pages (회원관리/랭킹관리/러닝데이터관리/랜드잇데이터관리/설정), each starting with `<main id="admin-content" hidden>` and calling `requireAdminSession(...)` from new `web/js/admin.js` before ever un-hiding content or rendering the layout — satisfies "세션 없으면 안쪽 페이지는 전부 안 보여야" by construction (a session-less visitor never sees anything but a redirect to `/admin/`, not even a flash of the shell). `renderAdminLayout(activeKey)` builds the header (reuses `.topbar`/`.brand`/`.brand-mark` from `/css/app.css` — same logo as the public site, per the user's requirement — plus a lone 로그아웃 button on the right, nothing else) and the left sidebar nav from a single `ADMIN_MENU` array, both in new `web/css/admin.css`. `admin.js` is intentionally independent of `app.js`/member's `localStorage` keys (own `pl_admin_session` key, own `ADMIN_API_BASE`, no JWT-reissue-on-401 logic since server sessions don't get reissued — a 401 just means log in again).

**2026-09-10 (same day, follow-up): 회원관리 메뉴 first content — list + search + pagination + detail with push-notification consent.** `GET /api/admin/members?q=&page=&size=` / `GET /api/admin/members/{memberSno}` (both under `AdminMemberController`, `admin.adapter.in.web`) delegate to a new cross-domain port `member.application.port.in.shared.AdminMemberQueryPort` — same shape as every other `*.shared` port in this codebase (admin never touches `member`'s repository directly). `MemberQueryService` (already `GetMemberNicknamePort, SearchMembersPort`) now also implements this one, gaining a `MemberAgreementRepositoryPort` dependency to look up the `PUSH_SERVICE` row from `member_agreement` (2026-09-10 agreement system, see above) for the detail response's `pushNotificationAgreed`/`pushNotificationAnswered` fields — `answered=false` (never asked, e.g. an app-only account that hasn't hit the login consent gate yet) is shown distinctly from `answered=true, agreed=false` (explicitly declined) in the web UI (unset/동의함/동의 안 함 badges), not collapsed into a single yes/no. List search matches `member_id`/`nickname` substrings and **includes withdrawn accounts** (new `MemberRepositoryPort.searchForAdmin`/`MemberJpaRepository` query, separate from the existing `searchByMemberIdOrNickname` used by the member-facing `/api/member/search` which filters withdrawn out) — an operator needs to see everyone, unlike the crew-invite-style member search. Returns a plain Spring Data `Page<AdminMemberSummary>` (same convention as `BoardQueryUseCase.listPosts`), size capped at 100 server-side. `web/admin/members.html` (search box + paginated table, row click navigates) and new `web/admin/member-detail.html` (info card + 푸시 알림 동의 badge) are plain fetch+render, no framework, matching every other admin/public page.

No migrations — all four read/write tables that already exist.

- **랭킹관리** (`AdminRankingController`, `/api/admin/ranking/records` + `/api/admin/ranking/territory`): two independently-paginated tabs, list-only (사용자 요청: "현재 랭킹리스트만 보여주자"). 기록랭킹 reuses `ranking` domain's existing `RankingProjection` native-query interface — `RankingJpaRepository.findAllBySeasonSno` is a new native query (with an explicit `countQuery`, required for native `Page<T>` methods since Spring can't auto-derive one) scoped to the current season via the same `GetCurrentSeasonPort` the public leaderboard already uses, just without the top-3/around-me windowing. 랜드잇랭킹 reuses `territory` domain's existing `TerritoryOwnerAreaProjection` — `TerritoryJpaRepository.findOwnersByAreaPaged` is the same owner/area group-by as the public `findTopOwnersByArea` but paginated instead of top-N-capped (its count query counts the *groups*, i.e. distinct owners, via a subquery — a plain `count(*)` would count raw territory rows instead).
